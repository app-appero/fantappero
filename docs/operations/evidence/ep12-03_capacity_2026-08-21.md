## Evoluzione della baseline e remediation

Il primo target globale esplorativo p95 <750 ms non è stato nascosto né adattato dopo il
run: con un solo worker API il diagnostico ha prodotto 2.532 richieste, 20,93 req/s e p95
2.787 ms (FAIL). Con quattro worker: 8.093 richieste, 66,77 req/s, p95 1.317 ms e 0%
errori, ma API prossima a circa quattro core; rosa (p95 2.679,97 ms) e formazione
(~1.470 ms) erano i path pesanti.

I budget per tier sono stati quindi proposti e congelati. Un full pre-remediation li ha
superati su steady/spike, ma ha fallito recovery: p95 2.192,33 ms contro 1.500 ms. La
ricognizione del codice ha identificato query ripetute per ogni atleta in risoluzione
ruolo/override/club. Le query sono state aggregate senza cambiare il contratto API.

Il test di regressione su rosa completa da 35 atleti misura ora 20 query per `/rosa`
(budget <=25) e 34 per `/formazione` (budget <=35). L'ispezione statica del codice
precedente indicava almeno circa 150 e 80 query rispettivamente; questi due valori sono
stime da struttura N+1, non misure runtime. I test funzionali team/lineup restano verdi.

## API, PostgreSQL e worker

Campionamento `docker stats` finale:

- steady: API CPU media 306,44%, picco 397,04%; PostgreSQL media 48,49%, picco 62,41%;
  worker media 30,00%, picco 101,73%; API ~461 MiB;
- spike/recovery: API media 344,14%, picco campionato 482,82%; PostgreSQL media 52,67%,
  picco 82,18%; worker media 4,22%, picco 21,61%; API ~478 MiB.

Il picco CPU indica che lo stack resta CPU-bound ad alto carico e non prova capacità
illimitata; il ceiling iniziale era circa quattro core. La remediation aumenta molto il
throughput e riduce la latenza, ma ogni crescita di carico/topologia richiede nuova
baseline.

`pg_stat_database`: 66.745 commit, 27 rollback, 562 block read, 3.236.052 hit, zero file
temporanei e zero deadlock; database 17.472.535 byte. Profondità coda Redis finale: 0.

Benchmark Celery su broker e worker reali (concorrenza 2): 100/100 ping completati,
p95 74,48 ms; 20/20 `fantasy_turns.ensure_upcoming`, p95 14,72 ms; ping finale worker
OK. Il task di dominio ha restituito zero leghe elaborate nel dataset, quindi misura
l'invocazione ma non un ricalcolo massivo.

`sports_data.poll_live_window` è completato in 300,28 ms con stato `skipped_disabled`,
zero fixture e zero richieste provider. Non esiste un trigger HTTP/SSE/WebSocket
rappresentativo: il risultato prova solo coda/invocazione, non carico live end-to-end.

Lo snapshot `/metrics` è esportabile in formato Prometheus ma, con quattro worker
Uvicorn, è process-local e non rappresenta il conteggio aggregato del run. Tutti i gate
HTTP riportati qui provengono da k6.
